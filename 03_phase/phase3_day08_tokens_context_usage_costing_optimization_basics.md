## 4. Core Theory: What Is a Token?

Explain simply:

**A token is a small unit of text processed by an AI model.**

It may be:
- a word
- part of a word
- punctuation
- number
- symbol
- formatting
- code fragment

AI models do not directly count text exactly the way humans count words. They process text as tokens.

### Simple explanation
“Tokens are like the billing and processing units of AI text.”

### Example approximation
This sentence:

```text
Create a summary of this document.
```

may become several tokens, not just one token per word.

### Trainer note
Do not spend too much time on exact tokenization mechanics. Learners need operational understanding, not tokenizer internals.

---

## 5. Why Tokens Matter

Tokens matter because they affect:

- how much information can fit into the model context
- how much the model has to process
- response speed
- cost
- ability to remember current conversation details
- quality of answer when context becomes too large
- risk of including unnecessary or sensitive information

### Verbatim explanation
“Tokens decide how much the model reads, how much it writes, and how much the usage can cost.”

---

## 6. Input Tokens and Output Tokens

Explain:

### Input tokens
Input tokens are tokens sent to the model.

They may include:
- user prompt
- system instructions
- conversation history
- project instructions
- memory
- selected file content
- tool descriptions
- tool outputs
- MCP tool schemas or results
- Skill descriptions
- code or document content

### Output tokens
Output tokens are tokens generated by the model.

They may include:
- answer
- plan
- explanation
- generated document
- generated code
- checklist
- table
- report
- final response

### Simple costing idea
In many AI pricing models:
- input tokens are charged
- output tokens are charged
- output tokens are often more expensive than input tokens
- different models have different prices

### Trainer explanation
“Input is what Claude reads. Output is what Claude writes. Both matter.”

---

## 7. Context Window

Explain:

**The context window is the amount of information the model can consider at one time.**

It is like the working desk of the model.

A bigger desk can hold more papers, but if we put too many unnecessary papers on it, work becomes slower, costlier, and noisier.

### Context may include:
- current prompt
- previous messages
- instructions
- files
- memory
- tool outputs
- MCP data
- Skill descriptions
- generated intermediate plans

### Verbatim explanation
“The context window is not the same as memory. Context is what the model sees for the current work. Memory is stored information that may be brought into context when relevant.”

---

## 8. Simple Example: Small vs Large Context

### Small context

```text
Summarize this 300-word note into 5 bullet points.
```

Likely token usage:
- small input
- small output
- low cost
- fast response

### Large context

```text
Read these 20 long documents, compare them, generate a detailed report, create a checklist, and propose next actions.
```

Likely token usage:
- large input
- large output
- more tool calls
- more context
- higher cost
- slower execution

### Trainer point
Large workflows may be valid, but they should be designed carefully.

---

## 9. Why Claude Code Can Use More Tokens Than Normal Chat

Claude Code can use more tokens because it may include or process:

- project files
- folder structure
- `CLAUDE.md`
- memory files
- Skill descriptions
- tool descriptions
- terminal outputs
- error logs
- test outputs
- code files
- document files
- MCP server information
- repeated planning steps
- repeated correction loops
- conversation history

### Example normal chat
```text
Explain what a project plan is.
```

### Example Claude Code task
```text
Inspect this project folder, read requirements, create plan, create risk register, generate output file, and review missing information.
```

The second task may require:
- file listing
- reading files
- generating plan
- creating output
- reviewing output
- possibly multiple turns

### Trainer explanation
“Agentic work has more context and more steps. More context and more steps usually mean more tokens.”

Teach this table.

| Source | How It Uses Tokens |
|---|---|
| User prompt | Direct instruction sent to model |
| Conversation history | Previous messages may be included |
| `CLAUDE.md` | Project instructions may load into context |
| Memory | Relevant stored context may be included |
| Skills | Skill descriptions/instructions may be included when relevant |
| Files | File content can add many tokens |
| Tool descriptions | Available tools may add context |
| Tool outputs | Command results, logs, search output, test output |
| MCP | Tool schemas, tool names, and returned data may add tokens |
| Output | Generated answer, file content, report, code, checklist |

### Trainer explanation
“Token usage is not only the visible prompt. Hidden or attached context may also contribute.”

## 11. `CLAUDE.md` and Token Usage

`CLAUDE.md` is useful, but it should not become unnecessarily long.

### Good `CLAUDE.md`
- clear
- stable
- project-level
- concise
- practical
- safety-focused
- avoids repeated examples unless needed

### Bad `CLAUDE.md`
- very long
- full of temporary task details
- repeats the same rules many times
- includes large examples unnecessarily
- contains outdated instructions
- mixes multiple unrelated projects
- includes sensitive information

### Trainer point
“`CLAUDE.md` should be strong but not bloated.”

---

## 12. Memory and Token Usage

Memory can save repeated prompting, but memory may also become context.

### Useful memory
- stable preferences
- repeated output format
- major project direction
- long-term style preference
- tool choice such as VS Code
- approval preference

### Wasteful memory
- temporary facts
- old decisions
- too many small details
- outdated tool choices
- sensitive information
- repeated or duplicate preferences

### Trainer explanation
“Good memory reduces repeated instruction. Bad memory adds noise.”

---

## 13. Skills and Token Usage

Skills can improve token efficiency when they replace repeated long instructions.

### Skill helps when:
- the same workflow is repeated
- the same output format is reused
- the same quality checks are needed
- the same safety rules apply

### Skill can hurt when:
- too many Skills are loaded or considered
- Skill descriptions are vague
- Skill instructions are unnecessarily long
- Skills overlap and confuse the agent
- examples inside Skills are too large

### Trainer explanation
“A Skill should contain the reusable method, not every possible example.”

---

## 14. MCP and Token Usage

MCP stands for Model Context Protocol. It is an open standard that allows AI applications to connect to tools and data sources.

In Claude Code workflows, MCP can be very useful because it may connect Claude to:
- files
- databases
- APIs
- documentation systems
- browsers
- issue trackers
- internal tools

But MCP can also increase token usage because it may add:
- tool names
- tool descriptions
- tool schemas
- server metadata
- tool results
- external data
- large returned outputs

### Trainer explanation
“MCP gives Claude Code more reach, but more reach can mean more context, more tokens, more security concerns, and more need for permission control.”

### Key rule
Use MCP only when it genuinely helps the workflow.

---

## 15. Files and Token Usage

Files can be one of the biggest sources of token usage.

### Small file
A short note may be cheap to process.

### Large file
A long PDF, report, log file, transcript, or codebase can be expensive to process if fully loaded.

### Better approach
Instead of:
```text
Read everything and tell me what matters.
```

Use:
```text
First inspect file names and headings. Then identify which files are relevant. Ask before reading large files fully.
```

### Trainer explanation
“Do not load the whole cupboard when you only need one file.”

---

## 16. Tool Output and Token Usage

Tool output can become very large.

Examples:
- full logs
- test output
- dependency tree
- long error traces
- database dumps
- command output from entire folder
- search result with too many matches

### Better approach
Ask for:
- summarized logs
- last 50 lines
- filtered output
- relevant error only
- file names first
- headings first
- dry-run summary instead of full dump

### Example

Bad:
```bash
cat huge-log-file.log
```

Better:
```bash
tail -n 100 huge-log-file.log
```

Better with filter:
```bash
grep -i "error" huge-log-file.log | tail -n 50
```

### Trainer explanation
“Tool output becomes context. Large tool output can increase cost and reduce clarity.”

## 17. Costing Basics

Explain carefully:

Claude pricing depends on:
- model selected
- input tokens
- output tokens
- cache usage where applicable
- long-context usage where applicable
- special features or platform setup
- API vs subscription/product usage model

### Important distinction
There may be different cost experiences depending on:
- Claude web/app subscription
- Claude Code usage model
- Anthropic API usage
- enterprise/team setup
- gateway/proxy setup

### General concept
Cost usually grows when:
- input is larger
- output is larger
- stronger model is used
- more turns are used
- tools return large results
- large files are repeatedly included
- long context is used
- multiple agents or retries are used

### Trainer explanation
“Even when exact billing depends on plan and setup, the usage logic remains the same: more context, more output, more turns, and stronger models usually mean higher cost.”

---

## 18. Current Pricing Concepts to Mention

Use this carefully as concept, not fixed memorization.

Anthropic publishes model pricing in USD per million tokens, with separate rates for input tokens and output tokens. Prompt caching has separate write and read rates, and batch processing can reduce cost for some API workflows.

Claude pricing can change, so learners should always check the official pricing page before making financial estimates.

### Trainer note
Do not ask learners to memorize prices. Teach them to understand the pricing structure:
- input
- output
- model
- cache
- long context
- batch
- usage tracking

---

## 19. Prompt Caching: Simple Concept

Explain:

Prompt caching can reduce cost when the same large context is reused across multiple requests.

### Example
If the same large instruction or reference material is repeatedly used, caching may allow later calls to reuse cached content more cheaply than sending it fresh each time.

### Useful for:
- repeated long system instructions
- repeated reference documents
- repeated static context
- API workflows with stable context

### Not useful for:
- constantly changing prompts
- one-time tasks
- small prompts where overhead is not worth it

### Trainer explanation
“Caching is useful when the same large context is reused. It is not magic; it works best with stable repeated context.”

---

## 20. Model Choice and Cost

Different models have different capabilities and costs.

General idea:
- stronger models may be better for complex reasoning, planning, and high-risk work
- smaller/faster models may be enough for simple formatting, summarization, or routine tasks
- use the right model for the right job

### Example
Use stronger model for:
- complex planning
- critical review
- architecture reasoning
- security-sensitive analysis
- difficult debugging
- multi-document synthesis

Use lighter model for:
- simple rewriting
- formatting
- basic extraction
- short summaries
- repetitive low-risk tasks

### Trainer explanation
“Optimization does not always mean using the cheapest model. It means using the right model for the task.”

---

## 21. Output Length and Cost

Output tokens often matter significantly.

Bad instruction:
```text
Explain everything in maximum detail.
```

Better instruction:
```text
Give a concise summary first. Ask before expanding into full detail.
```

Bad instruction:
```text
Generate a complete 50-page guide immediately.
```

Better instruction:
```text
First create an outline. After approval, generate one section at a time.
```

### Trainer explanation
“Long output should be intentional, not accidental.”

---

## 22. Agentic Loop Cost

In Claude Code, a task may involve multiple steps.

Example:
1. understand task
2. inspect files
3. read selected files
4. create plan
5. edit file
6. run command
7. inspect error
8. fix output
9. create summary
10. ask for review

Each step may involve tokens.

### Cost risk
If the instruction is unclear, the agent may:
- read too many files
- produce long explanations
- retry many times
- run unnecessary commands
- create excessive output
- keep asking and answering in loops

### Trainer explanation
“A badly defined task can cost more because the agent spends tokens figuring out what should have been clear.”

---

## 23. Token Optimization Principles

Teach these principles.

### Principle 1: Be clear
Clear instructions reduce unnecessary back-and-forth.

### Principle 2: Scope the task
Tell Claude Code what to include and exclude.

### Principle 3: Start with index/summary
Inspect structure before loading full content.

### Principle 4: Use relevant files only
Do not ask it to read everything unless needed.

### Principle 5: Keep `CLAUDE.md` concise
Project rules should be clear, not bloated.

### Principle 6: Keep memory clean
Remove outdated or irrelevant memory.

### Principle 7: Use Skills for repeated methods
Avoid repeating long instructions.

### Principle 8: Limit MCP tools
Connect only tools needed for the workflow.

### Principle 9: Control output length
Ask for outline first, then expand.

### Principle 10: Use approval checkpoints
Avoid long uncontrolled agent loops.

## 24. Good vs Bad Token-Aware Prompts

### Bad
```text
Read everything in this folder and make a complete report.
```

Problem:
- too broad
- may load irrelevant files
- large context
- expensive
- unclear output

### Better
```text
First list the files and identify which ones seem relevant to creating a project summary. Do not read large files fully yet. Show me the proposed files to inspect before continuing.
```

Why better:
- staged
- controlled
- lower initial token use
- human approval before more context

---

### Bad
```text
Use all previous messages and all files to create a complete guide.
```

Problem:
- huge context
- unclear relevance
- high output tokens

### Better
```text
Use only the approved outline and the files in input/. Create Section 1 first in under 800 words. Mark missing information clearly.
```

Why better:
- scoped
- controlled output
- avoids unnecessary context

---

### Bad
```text
Explain every error in this huge log.
```

Problem:
- too much log content
- high token usage
- may be noisy

### Better
```text
Inspect only the last 100 lines of the log and summarize recurring errors. Do not include full log text unless needed.
```

Why better:
- limited context
- focused result
- lower cost

## 25. Optimization Does Not Mean Removing Safety

This is very important.

Do not remove:
- privacy rules
- approval rules
- do-not-do rules
- uncertainty rules
- human review rules
- source validation rules

Instead, remove:
- repeated wording
- outdated instructions
- irrelevant examples
- unnecessary file content
- unnecessary long output
- unrelated tools
- duplicate memory

### Verbatim explanation
“Cost optimization should reduce waste, not remove safety.”

---

## 26. Practical Optimization Checklist

Before starting a Claude Code task, ask:

1. What is the exact goal?
2. Which files are required?
3. Can we inspect file names first?
4. Can we avoid reading large files fully?
5. Is `CLAUDE.md` concise and current?
6. Is memory relevant and current?
7. Is a Skill available for this repeated task?
8. Are MCP tools really needed?
9. Can output be limited first?
10. Can we work in phases?
11. Can we ask for outline before full generation?
12. Can we use sample data first?
13. Can we avoid unnecessary retries?
14. Does the task require a stronger model?
15. What approval checkpoints are needed?

## 27. Activity: Identify Token Waste

Ask learners to review these workflows and identify waste.

### Workflow 1
```text
Claude Code is asked to read an entire project folder, including archives, old drafts, large logs, and screenshots, to create a 1-page summary.
```

Waste:
- unnecessary old files
- large logs
- irrelevant archive
- too much context for small output

Better:
```text
Read README and current input files first. Ignore archive and logs unless needed.
```

---

### Workflow 2
```text
`CLAUDE.md` contains 20 pages of repeated instructions, old project history, and many examples.
```

Waste:
- bloated project instructions
- outdated context
- repeated rules

Better:
```text
Create concise project rules and move examples to separate optional files.
```

---

### Workflow 3
```text
MCP connects to many tools, but the task only requires reviewing one local Markdown file.
```

Waste:
- unnecessary tool context
- possible security exposure
- irrelevant capabilities

Better:
```text
Use local file context only. Disable or avoid unrelated tools for this task.
```

---

### Workflow 4
```text
Claude Code is asked to generate a full 30-page manual without outline approval.
```

Waste:
- large output
- possible wrong structure
- expensive correction cycle

Better:
```text
Generate outline first. After approval, generate one section at a time.
```

---

## 28. Mini Exercise: Rewrite for Token Efficiency

Ask learners to improve this prompt:

```text
Read everything, understand everything, and make a detailed complete document with all possible points and examples.
```

Expected improved version:

```text
First inspect the available files and list the ones relevant to creating the document. Do not read large files fully yet. Propose an outline with section headings and missing information. Wait for approval before generating the full document.
```

### Trainer point
The improved prompt saves tokens, improves control, and reduces rework.

## 29. Common Mistakes to Correct

### Mistake 1
Thinking only visible text uses tokens.

Correction:
Instructions, memory, tool results, file content, Skills, and MCP context may also contribute.

### Mistake 2
Putting everything into `CLAUDE.md`.

Correction:
Keep `CLAUDE.md` concise and project-level.

### Mistake 3
Saving too much memory.

Correction:
Store only stable, useful, safe context.

### Mistake 4
Using Skills for one-time tasks.

Correction:
Use Skills for repeated workflows.

### Mistake 5
Connecting unnecessary MCP tools.

Correction:
Use only relevant MCP tools.

### Mistake 6
Asking for large output too early.

Correction:
Ask for outline first.

### Mistake 7
Using strong model for every small task.

Correction:
Match model to task complexity.

### Mistake 8
Removing safety instructions to save tokens.

Correction:
Reduce waste, not safety.
